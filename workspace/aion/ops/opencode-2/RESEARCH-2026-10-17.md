# OpenCode 2.0 — capability and feature research

**As of:** 2026-10-17. **Method:** authoritative OpenCode 2.0 announcement + V2 documentation and migration guide, supplemented by clearly identified upstream issue reports. This is a *documentation research result*, not a measured performance benchmark. URLs appear in [RISKS-AND-SOURCES.md](./RISKS-AND-SOURCES.md).

## Executive conclusion
OpenCode 2.0 is a released major version (not hypothetical). The important shift for AION is from scattered CLI invocations to an **auto-discovered, shared background service** with a typed HTTP client, programmable tools, native background execution, plugin extension points, and an embeddable SDK. It could simplify session control and observing code-production work, but an immediate upgrade would expose AION to API breakage, unsupported V1 plugins, new default permissions and service-lifecycle risk. Prefer an isolated pilot.

## Capability inventory (confirmed in official OpenCode V2 documentation)
| ID | Capability | Actual V2 behavior / boundary | AION relevance |
|---|---|---|---|
| F01 | One local service | Auto-started/discovered shared background server owns sessions, permissions, plugins, configuration, tool work; TUI, desktop and web connect | One runtime supervision point |
| F02 | Isolated operation | `opencode --standalone` starts private server; `--server URL` connects explicitly | Test without interfering with active service |
| F03 | Service lifecycle | `opencode service status/start/stop/restart`; `opencode api get /api/info` health | Runtime health gates, not guaranteed uptime |
| F04 | Pairing | `opencode pair`, local authenticated pairing and service connections; intentional network exposure required for remote clients | Potential phone/other-machine integration, security review first |
| F05 | Rebuilt HTTP API | V2 endpoints/contract *not backward compatible* with V1 | Replace V1 SDK/server calls, version pin adapters |
| F06 | TypeScript/JS client | `@opencode/client` supports sessions, prompt, events and service discovery via `@opencode/client/service` | Strong first-choice adapter for ZCode/AION |
| F07 | Live event stream | `client.event.subscribe()` produces async events; **live-only, no replay or automatic reconnection** | Must snapshot/reconcile after gaps; not durable evidence on its own |
| F08 | Code Mode | `@opencode/codemode` translates MCP/OpenAPI tools into functions composable in code | Fewer model turns, lower tool-catalog context overhead (upstream design claim, not our measurement) |
| F09 | MCP in Code Mode | MCP sources participate by default in code-mode tool discovery | Model can compose heterogeneous provider tools |
| F10 | Background subagents | Primary agent can delegate concurrent subagent tasks, including alternate models | Parallel review/build/check roles |
| F11 | Background shell commands | Async shell and foreground-to-background handoff | Builds/tests without blocking conversation |
| F12 | Plugin API rewrite | `@opencode/plugin`, default `Plugin.define({ id, setup(ctx) })` and domain hooks/transforms | First-class AION tools and policy hooks after migration |
| F13 | Stable TUI plugins | OpenTUI-based client extension promoted to stable; plugin hot reload supported | Optional local operator UX; not priority over execution |
| F14 | Embeddable SDK | `@opencode/sdk`, optional developing Effect API; runtime can serve standard protocol | Possible custom execution runtime later; avoid premature fork |
| F15 | Native agents & models | `agents` configuration, file-based definitions and model variant syntax `provider/model#variant` | Map worker roles to models and permissions |
| F16 | Ordered permissions | Explicit ordered `permissions` rules for shell/edit/websearch/external_directory etc. | Least privilege and host boundaries |
| F17 | Location scoping | Client/plugin APIs carry directory/project context | Enforce worktree-per-task and attribution |
| F18 | Plugin RPC | Typed `client.rpc` and subscription interfaces for custom plugin methods | Structured AION extension points |
| F19 | CLI automation | `opencode run` and `opencode mini` remain available | Noninteractive fallback/diagnostic use |
| F20 | Paths/SQLite | `opencode debug paths db`; background state and persistent DB; direct DB edits not recommended | Inspect supported data safely; app API is preferred |
| F21 | Config compatibility | Most supported V1 config/agents/skills work in V2, with native V2 form optional | Gradual migration, not rewrite-everything |
| F22 | Windows binary & desktop | Windows x64 binaries and desktop app published; **official V2 docs say Windows package managers unsupported** | Evaluate portable/approved packaging; do not assume winget |
| F23 | Provider controls | Provider/model configurations plus first-class policy surface | Future model routing with controlled provider availability |
| F24 | SDK client independence | Network client can run separately; service `ensure()` is Node-specific | Separate read-only dashboards from privileged host control |
| F25 | Code-first customization | Core itself uses 80+ internal plugins per announcement, and supports hot reload | Capability multiplier; not an assertion all external plugins are compatible |

## Key architecture
```text
AION GitHub task/evidence ledger
            |
     Authorized dispatcher / ZCode transport (where applicable)
            |
   Explicit AION adapter (versioned, correlated, permissioned)
            |
   @opencode/client v2 OR carefully gated CLI
            |
   OpenCode V2 background service (shared for host)
       |          |            |
   sessions     tools       plugins / policies
       |          |            |
   model runs   shell      MCP Code Mode
            |
  sanitized receipts and evidence -> AION GitHub ledger
```
AION relay envelopes, ACP JSON-RPC, OpenCode REST/API and MCP tool calls are *four distinct protocols*. Each translation gets its own validated schema/correlation IDs.

## V1 -> V2 breaking contracts (official migration guide)
1. **Plugins:** V1 plugin functions/hooks do not execute in V2. Port to `@opencode/plugin` default `Plugin.define` with stable `id`, `setup`, scoped transforms and hooks. Merely renaming config entries is insufficient.
2. **Server API:** completely revised. Prefer `@opencode/client`; do not attempt direct substitution of old REST paths or SDK call shapes.
3. **TUI settings:** project/layered `tui.json(c)` becomes global `~/.config/opencode/cli.json`, auto-migrated where supported.
4. **Permissions:** legacy `bash` -> `shell`, `task` -> `subagent`, `write/patch` -> `edit`. V2 **allows external_directory by default**, unlike V1 ask behavior; restore ask rule explicitly.
5. **Agents:** `agent` or `mode` -> `agents`; `prompt` -> `system`; `disable` -> `disabled`; `variant` becomes `model#variant`; `maxSteps` -> `steps`.
6. **MCP:** `mcp` entries nested under `mcp.servers`; `enabled` -> `disabled` inverted; split timeouts into catalog/execution.
7. **Models/providers:** `provider` -> `providers`; `npm` -> `package`; provider URL -> `settings.baseURL`; variants array; model capabilities explicit.
8. **Compaction/skills/commands:** `compaction.keep.tokens` and `buffer`; skills array; `commands` and `subagent`.
9. **LSP caveat:** V2 *accepts* legacy `lsp` config but **does not run language servers / expose LSP diagnostics**. Substitute compiler/lint/typecheck when relevant.
10. **Instructions:** V2 discovers `AGENTS.md`, not the old implicit `CLAUDE.md` fallback; explicitly migrate relevant instructions.
11. **Configuration compatibility:** supported V1 fields may remain; ignored legacy fields generate warnings. Avoid converting the config in place while a V1 instance still consumes it.
12. **Sharing:** do not assume V1 native public share links exist in V2; use private sanitized exports/repo evidence and confirm runtime capabilities.

## What not to infer from the release announcement
- Background work is *possible*, not proof AION's task engine runs continuously or reliably on this host.
- Auto-discovery is not a cross-machine authenticated task bus and is not a substitute for explicit task admission/receipts.
- Code Mode efficiency is a design advantage, not an AION-measured latency/cost saving.
- 80+ internal plugins are not a guarantee every V1 community plugin was ported.
- Having `client.event.subscribe()` does *not* provide replay, durable delivery, or exactly-once execution.
- A passing mock prompt isn't evidence of authenticated ChatGPT browser operation.
- Version 2.x release notes may be sparse; pin and compare specific releases before claiming patch-level fixes.

## Priority for AION
**P0:** existing Windows v1 API/plugin/permission inventory; host storage gate (PC HQ); current service/session baseline; 2.0 isolated smoke test.  
**P1:** typed client adapter and minimal evidence/telemetry integration; verify session IDs, events, sanitized exports and recovery.  
**P2:** code-mode MCP benchmarks and one background subagent workflow with durable proof.  
**P3:** specialized plugins, model-routing optimization, remote pairing and SDK embedding after P0/P1 gates.
