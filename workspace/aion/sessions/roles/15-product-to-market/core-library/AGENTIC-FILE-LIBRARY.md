## B. Provider-recognized conventions — verified external documentation

| Agent / format | Recognized names and key behavior | Authority link |
| --- | --- | --- |
| **AGENTS.md open convention** | Root and scoped/nested `AGENTS.md` for agent-oriented instructions; the file is ordinary Markdown, not a fixed schema | [agents.md](https://agents.md/) |
| **OpenCode V2** | `AGENTS.md` in global/repo/subdirectories; V2 does **not** use `CLAUDE.md` as fallback. `opencode.json[c]` can include additional instruction paths. **Do not apply older OpenCode V1 fallback documentation to V2.** | [OpenCode V2 instructions](https://opencode.ai/v2/docs/instructions) |
| **Claude Code** | Root and nested `CLAUDE.md`; scoped Markdown in `.claude/rules/` | [Claude help: context files](https://support.claude.com/en/articles/14553240-give-claude-context-claude-md-and-better-prompts) · [VS Code format mapping](https://github.com/microsoft/vscode-docs/blob/main/docs/agent-customization/custom-instructions.md) |
| **Gemini CLI** | Default `GEMINI.md`, hierarchical discovery and configurable alternative filenames through `context.fileName`; loading semantics are Gemini-specific | [Gemini CLI context](https://geminicli.com/docs/cli/gemini-md/) |
| **GitHub Copilot** | Repo-wide `.github/copilot-instructions.md`, scoped `.github/instructions/**/*.instructions.md`, and certain agent instruction files depending on surface | [GitHub Copilot custom instructions](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions) · [support matrix](https://docs.github.com/en/copilot/reference/custom-instructions-support) |
| **Cursor** | `.cursor/rules/*.mdc` metadata-bearing project rules; also supports `AGENTS.md` as a simpler alternative; `.cursorrules` is legacy | [Cursor rules](https://cursor.com/docs/rules) |
| **Agent Skills** | A skill directory with required `SKILL.md` (YAML frontmatter with `name` and `description`), optional `scripts/`, `references/`, `assets/`; activate lazily | [Agent Skills source/spec](https://github.com/agentskills/agentskills/blob/main/docs/home.mdx) |

**Version caveat:** Provider discovery, precedence, frontmatter and nesting behavior are *not identical*. Compatibility must be tested against the exact installed tool/version, especially OpenCode V2. Do not normalize path casing blindly on Windows or assume `CLAUDE.md`/ `GEMINI.md` are substitutes for `AGENTS.md` in every tool.

## C. How these files are wired (product logic)

```
repo/workspace scope
   → scan actual files / paths / hashes / timestamps
   → classify by family and file-origin/status
       native-recognized | project-observed | local custom | proposed
   → provider-compatibility resolver
       detects actual tool and version + loading/precedence + scope
   → logical document role
       law/instruction | context | task | memory | handoff | evidence | historical
   → authority/conflict evaluator
       user intent & project policy; duplicate, outdated, contradictory, untrusted donor sources
   → minimal, provenance-linked context bundle for chosen agent
   → optional explicitly requested artifact generation / link wiring
   → observe outcomes and record source/version/receipt
```

**Every catalog entry should carry**: `id`, `family`, `literalPathOrGlob`, `recognizedBy`, `versionConstraint`, `purpose`, `sourceUri`, `originType`, `scope`, `precedence`, `risk/trust`, `contentHash`, `lastVerified`, `owner`, `lifecycle`, `relationships`. `originType` should distinguish official vendor documentation, actual repository file, prior-conversation reconstruction and VIVIM proposal. Never conflate these.

### File relationship graph

- **Instruction pointers:** `AGENTS.md` or native vendor file → concise repo-wide rules → scoped specialist guidance; honor native nesting and precedence.
- **Skill references:** provider-recognized skill directory / `SKILL.md` → optional `references/` and `scripts/` only when a relevant skill is activated.
- **Execution continuity:** `TASKS.md` / issue → `PLAN.md` when needed → actual code/tool event → `EVIDENCE.md` or receipt → `HANDOFF.md` / `CLOSEOUT_PROTOCOL.md` if useful; not every step requires a separate file.
- **Context longevity:** `PROJECT-CONTEXT.md` / `MEMORY.md` → dated/source-backed facts and version pointers; `STATE.md` / `SITREP.md` are transient snapshots, not permanent truth.
- **Governance:** current human instruction and existing owner policies outrank stale donor AGENTS files; provider auto-loading means **untrusted files must be read as source data only** in harvests, not adopted as execution mandates.

## D. Product target, not a document factory

For VIVIM core, provide a **read-only inventory** first with on-demand visual matrix:

1. **Discover** what agentic files really exist across repositories, nesting, provider configs and source history. No hallucinated path or auto-creation.
2. **Compare** family, compatibility, precedence, duplicate content, divergent guidance and orphaned instruction links.
3. **Resolve** a minimally sufficient applicable context for a chosen agent/tool and task; retain source/recency/confidence.
4. **Generate only when requested** a small role-appropriate kit or provider adapter from a single reconciled logical source; preserve source provenance and avoid redundant copies.
5. **Trace** commands (Toolkit 01) to their relevant schemas/instructions and outcomes, without confusing a Markdown directive with an authorization or installed runtime.

**Core MVP exemplar:** one root `AGENTS.md` (when supported), one chosen provider-native config only when actually necessary, and targeted `SKILL.md` assets. Add `HANDOFF.md`, `STATE.md` or `CLOSEOUT_PROTOCOL.md` only when actual continuity/proof needs warrant them. **Never mass-generate 133 files.**
