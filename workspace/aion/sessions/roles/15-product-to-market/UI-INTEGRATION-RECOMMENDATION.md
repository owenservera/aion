## Decision — Option A, evolve the existing Harness ESM/HTML World shell

**Choose Option A now.** The current `/chat` route serves `chat.html` → `chat.mjs`, which dynamically mounts `world-view.mjs` into existing `#worldShell` with `#shellModes` and the existing `createRichRenderer`. World API is served from `world-service.mjs` via the existing Studio server. This is implemented source, not a greenfield UI gap: [vivim-harness/src/studio/ui/chat.mjs](https://github.com/owenservera/vivim-harness/blob/1a9de9967f5e0b622f75f7d726ba6a356b8a9c51/src/studio/ui/chat.mjs#L1878-L1906); [vivim-harness/src/studio/ui/world-view.mjs](https://github.com/owenservera/vivim-harness/blob/1a9de9967f5e0b622f75f7d726ba6a356b8a9c51/src/studio/ui/world-view.mjs#L674-L787); [vivim-harness/src/studio/world-service.mjs](https://github.com/owenservera/vivim-harness/blob/1a9de9967f5e0b622f75f7d726ba6a356b8a9c51/src/studio/world-service.mjs#L169-L195).

| Decision axis | A — existing HTML/ESM (**selected**) | B — port Final React | C — new slim frontend |
|---|---|---|---|
| Framework/build | No framework migration; existing Node/browser ESM and test fixtures | Next/React providers, SDK state and build migration | New bundler/routing/design/testing lifecycle |
| Data/storage | Reuses World service + VersionedStore and saved DOM evidence | Final slot/conversation/storage assumptions conflict | Can consume APIs but duplicates client routing and identity state |
| Browser effects | Existing singular Harness CDP/drive owner | Final `/api/setup/launch-visible`, `verify`, `kill` could introduce second actor | Risk if composer reimplements send or connection |
| Auth/contracts | Existing same-origin Studio access and `/api/v1/world` | Final `/api/setup/*`, `/api/search`, `/api/storage/*`, `/api/conversations` incompatible without explicit adapters | Must bridge existing auth, exact thread IDs and failure/reconciliation semantics |
| Risk/rollback | Feature-gated additive DOM functionality | Frontend rewrite + foreign dependencies | Parallel application risk |
| First-user benefit | Fastest narrow increments over real mounted UI | More visual assets, slower first value | Not justified by inspected UI gaps |

**No wholesale React components are classified B/direct reuse.** Reuse interaction language and small source algorithms only where tested against the actual Harness contract. MIT repo-level files exist for Final and Platform, but third-party dependency, generated asset and attribution terms still need independent review.

## Stop conditions and ownership
- UI owns only views/interactions, not Core service semantics. Product Agent owns approved first-user journeys and parked decisions. Core owns new read-only account/world/root APIs and any data relocation transactions. QA owns live browser/Windows receipts. No local agent was asked to run anything in this audit.
- Preserve **three distinct domains**: personal data workspace directory, Chrome world/profile, in-app workspace/project view. Selection ≠ send authorization; error/uncertainty never triggers an automatic resend.
- Avoid unapproved sync. Keep current cross-OS Node/HTML/ESM behavior. Manual Windows and Linux verification remains required for new UI dependencies.
- This document is **implementation-ready analysis**, not permission to implement parked features or a claim of passing tests.
